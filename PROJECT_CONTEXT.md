# Project Context: SuperDesk (SuperProfile Hiring Assignment)

Reference this file at the start of every Cursor session on this project. It should not go stale as the build progresses. Update it if a decision changes.

## What this is
A 36-hour hiring assignment for SuperProfile (Cosmofeed). Build a production-ready customer communication platform (live chat, email, unified inbox, knowledge base, AI summarization, custom domains). Built solo. Evaluated on the same rubric as engineering candidates, so code quality and architecture reasoning both matter, not just feature completeness.

## Tech stack
- **Framework:** Next.js 14, App Router, TypeScript
- **Hosting:** Vercel
- **Database, Auth, Realtime:** Supabase (Postgres + Supabase Auth + Supabase Realtime)
- **Email:** Postmark (inbound parsing via webhook, outbound sending, Message-ID / In-Reply-To threading)
- **AI:** OpenAI API, `gpt-5.4-mini` (issue summarization, AI auto-reply drafts). Reasoning effort is set to `none` — these are extraction and drafting tasks, not multi-step thinking.
- **Custom domains:** Vercel Domains API (add domain to project programmatically, Vercel auto-provisions SSL)

## Non-negotiable requirements (all 7 required, partial submissions not reviewed)
1. Auth + team management: signup/login, invite teammates, remove teammates, roles (Admin, Agent), agent assignment to conversations
2. Chat bubble: embeddable single-script-tag widget, real-time messaging, typing indicators, online/offline status, read receipts, persisted history
3. Email channel: inbound parsing into conversations, reply from dashboard sends real email, proper threading
4. Unified inbox: chat + email in one view, filter by channel/assignee/status, assign/reassign/snooze/resolve
5. Knowledge base: rich text editor, categories, public searchable page, auto-suggest inside widget
6. AI issue summarization: summary on open, updates as conversation progresses
7. Custom domains: workspace connects own domain for KB, SSL provisioning, documented approach even if DNS verification is stubbed

## Stretch features (chosen, build only after all 7 above are solid)
- AI auto-reply drafts (reuses the same LLM call pattern + KB data as summarization)
- Analytics dashboard (response times, resolution rates, agent performance)

- SLA tracking with business-hours awareness (phase 8b, done)

Not building: canned responses, contact timeline (explicitly cut from this submission), webhooks/API. Documented as deferred, not attempted.

## Architecture decisions

**Realtime:** Supabase Realtime, not raw WebSockets or Socket.io. Three channel types in use:
- Postgres Changes on the `messages` table → broadcasts new messages to subscribers of `conversation:{id}`
- Broadcast (ephemeral, not persisted) for typing indicators
- Presence, one channel per workspace, for agent/visitor online status

**Widget embed:** JS SDK injected directly into the host page's DOM (not an iframe). UI wrapped in Shadow DOM (`element.attachShadow`) so host page CSS can't collide with widget styles and vice versa.

**CORS:** Widget writes go through Next.js API routes (not direct-to-Supabase from the browser), so we get input validation and rate limiting. Routes validate the request's origin against that workspace's `allowed_widget_domains`. This is also the tenant isolation story: a workspace's widget only works from domains that workspace registered.

**Visitor identity:**
- Default: anonymous token generated on first widget load, stored in the host page's localStorage (first-party, since the widget is DOM-injected not iframed). Contact row created with `anonymous_token` set, `email` null.
- If the host page calls `boot({ email })`, look up contact by `(workspace_id, email)` first. Found → use that contact. Not found → create it, and attach the current localStorage token to that same row if one exists.
- Known limitation (documented, not solved): the same person on two different browsers with no email will appear as two separate contacts. Real Intercom solves this with a merge flow; out of scope for 48 hours.

## Database schema
Built in `supabase/migrations`. All tables have UUID PKs and `created_at` / `updated_at`.
- `workspaces` (id, name, slug, custom_domain, custom_domain_status, custom_domain_verified_at, allowed_widget_domains[], inbound_token, first_response_target_minutes, resolution_target_minutes, business_hours_start, business_hours_end, business_days[], business_timezone)
- `profiles` (id, auth_user_id, workspace_id, role: admin | agent, email, full_name)
- `workspace_invites` (id, workspace_id, email, role, token, invited_by, expires_at, accepted_at)
- `contacts` (id, workspace_id, anonymous_token, email nullable, last_seen_at)
- `conversations` (id, workspace_id, contact_id, channel: chat | email, status: open | snoozed | resolved, assigned_agent_id, last_message_at, subject, ai_summary, ai_summary_updated_at, ai_summary_message_count, resolved_at, snoozed_at, total_snoozed_seconds)
- `messages` (id, workspace_id, conversation_id, sender_type: contact | agent | system, sender_id, body, created_at, email_message_id nullable, email_in_reply_to nullable)
- `kb_categories` (id, workspace_id, name), `kb_articles` (id, workspace_id, category_id, title, slug, body, published, search_vector)

All tables scoped by `workspace_id` with Row Level Security policies, not just app-level checks. This is one of the eval criteria (tenant isolation). Proven by `supabase/tests/rls_isolation.sql`, which probes every policy as a real `authenticated` user across two workspaces.

Additions to the original sketch, all deliberate:
- `workspace_invites` — required by the invite flow, which the sketch did not cover.
- `profiles.email` / `full_name` — clients cannot read `auth.users`, so the team list needs a local copy. Written only by the two bootstrap functions.
- `messages.workspace_id` — denormalised from `conversations` so the RLS policy is a column comparison instead of a join, and so Realtime can filter by workspace in phase 2.
- Composite FKs, e.g. `conversations (contact_id, workspace_id) → contacts (id, workspace_id)`. A cross-tenant id is rejected by the database itself, not only by RLS.
- `profiles.auth_user_id` is unique, so one account belongs to exactly one workspace. Simplifies every policy; revisit if multi-workspace membership is ever needed.
- `workspaces.inbound_token` — Postmark delivers all inbound email for the account to one webhook, so the payload's `MailboxHash` is the only tenant signal. The token is the plus-suffix of the workspace's inbound address. Generated by a column `DEFAULT` (9 random bytes, lowercase hex) rather than in application code, so no insert path can create a workspace without one.
- `conversations.subject` — email threads need a subject to reply with; chat leaves it null.
- `conversations.ai_summary` / `ai_summary_updated_at` / `ai_summary_message_count` — cached issue summary. The count is how many messages the stored summary reflects, so the inbox can skip the model when nothing new has been said and, when it has, send only the delta instead of the whole thread.
- `conversations.resolved_at` — set by a `BEFORE INSERT OR UPDATE OF status` trigger when status crosses into `resolved`, cleared when it leaves. Re-resolving after a reopen gets a fresh timestamp. Backfilled from `updated_at` for rows already resolved at migration time. Check constraint keeps `resolved_at` non-null iff `status = 'resolved'`. Partial index on `(workspace_id, resolved_at desc)` for future date-range analytics.
- The pre-existing unique index on `messages (workspace_id, email_message_id)` is what makes the inbound webhook idempotent.
- `workspaces.slug` (globally unique) and `kb_articles.slug` (unique per workspace) — the public KB URLs. Both are written by `BEFORE INSERT` triggers, never by application code, so no insert path can produce a row that is unreachable by URL. A placeholder column DEFAULT exists purely so the generated `Insert` type does not demand a slug the caller has no business choosing. Workspace slugs are never regenerated on rename; article slugs regenerate while the article is a draft and freeze on first publish, so a live URL does not break on a retitle.
- `workspaces.custom_domain_status` / `custom_domain_verified_at` — the serving gate for custom domains. `custom_domain` alone is only what an admin typed into a form, so routing on it would let a workspace claim a hostname it does not own; only `verified` is ever served. A check constraint keeps the column to bare lowercase hostnames because the router compares it against the raw Host header, and a second one keeps status and domain consistent so the router never has to reason about a half-set row. Deliberately *not* in `anon`'s column grants: which workspace owns which hostname is not public information.
- `conversations.snoozed_at` / `total_snoozed_seconds` — the snooze ledger the resolution SLA subtracts. Same trigger shape as `resolved_at`: entering `snoozed` stamps `snoozed_at`, leaving it banks the elapsed time and clears the stamp, with a check constraint keeping `snoozed_at` non-null iff `status = 'snoozed'`. In the database rather than in the dashboard action because the Postmark inbound webhook also reopens snoozed threads. The banked value is **business** seconds, not wall-clock, so it is the same unit as the span it is subtracted from — wall-clock would over-credit a weekend snooze by ~64 hours and erase a real breach.
- `workspaces.first_response_target_minutes` / `resolution_target_minutes` / `business_hours_start` / `business_hours_end` / `business_days[]` / `business_timezone` — the SLA schedule. All defaulted (30 min / 24 h / 09:00–18:00 / Mon–Fri / Asia/Kolkata) so SLA is live for every existing workspace without an admin touching anything. `business_days` is ISO day-of-week to match `extract(isodow)`. Target upper bounds are a cost control, not politeness: the business-seconds function walks calendar days. Overnight windows are rejected by a check constraint rather than supported. The timezone is validated by a trigger against `pg_timezone_names`, because a CHECK expression cannot query a view and an unknown zone would make every SLA read for that workspace throw.
- `kb_articles.search_vector` — a stored generated `tsvector`, title weighted A and body B. Tags are stripped with an immutable regexp before indexing, which is what allows a generated column instead of a trigger that could drift from the rows.

**Public KB access (the one non-`auth.uid()` pattern):** an anonymous visitor has no uid, so no existing policy can ever grant it a row. Phase 5 adds separate additive `to anon` SELECT policies — published articles, the categories holding at least one, and the workspaces owning at least one — with the authenticated policies untouched. Two independent gates: those row policies, plus column-level `GRANT SELECT (…)` so a row-filter mistake still cannot expose `inbound_token` or `allowed_widget_domains`, and no write grant exists at all. Public reads go through `lib/supabase/anon.ts`, a session-less client, so a signed-in agent visiting the help centre gets `anon` rather than their own drafts.

**RLS mechanics:** policies compare `workspace_id` to `private.current_workspace_id()`, a `SECURITY DEFINER` helper. It sits in `private` rather than `public` because Supabase grants EXECUTE on all public functions to `anon`/`authenticated`, which would expose it over REST. Signup and invite acceptance run through `public.create_workspace_with_admin` / `public.accept_workspace_invite`, `SECURITY DEFINER` and granted to `service_role` only, so each multi-table write is atomic and unreachable from the browser. Role escalation is blocked by column-level grants: `authenticated` may only ever UPDATE `profiles.full_name`. Teammate removal is a profile DELETE, not a status column: `profiles_delete_admin` (admin, same workspace, not self — self-delete would orphan the workspace). Conversations they held become unassigned via `on delete set null (assigned_agent_id)`. The auth user is left in place so a later invite reattaches a profile to the same login. Pause/deactivate is deferred: a `paused_at` column would need a SECURITY DEFINER writer, because granting UPDATE on it would let `profiles_update_self` unpause a deactivated agent (RLS WITH CHECK cannot see OLD). Re-invite is the reversible path.

## Build sequence (one prompt per phase, roughly)
1. **Done.** Scaffold, DB schema + RLS, auth, team roles, workspace creation, invite flow, empty dashboard shell. Invites are delivered as a shared link, not email — outbound email lands in phase 3.
2. **Done.** Embeddable chat widget (Shadow DOM, esbuild bundle ~21 KB gzipped), CORS-validated API routes, Supabase Realtime (broadcast messages, typing, presence), dashboard live chat view with Postgres Changes, reconnect re-fetch. Rate limiting deferred to phase 3 alongside the email channel.
3. **Done.** Email channel. Inbound webhook at `/api/webhooks/postmark-inbound`, protected by Basic Auth (credentials embedded in the Postmark webhook URL) plus a source-IP allowlist. Tenant routing on `MailboxHash` → `workspaces.inbound_token`; thread resolution on `In-Reply-To`/`References` → `messages.email_message_id`, never on the sender address. We mint our own RFC `Message-ID` and send it with `X-PM-KeepID: true`, because Postmark's returned `MessageID` is a delivery id that never appears in anyone's headers. Idempotent by unique index; 200 on anything a retry could not fix. Rate limiting still deferred.
4. **Done.** Unified inbox filters + conversation actions. Filter bar (status/channel/assignee) with URL-encoded state (`window.history.replaceState` keeps filters shareable and refresh-safe without triggering RSC re-renders). Default view: Open / all channels / all agents, with a one-click "Me" chip. Assign/reassign from both list row and thread header; server validates target agent belongs to same workspace before updating. Snooze/resolve/reopen via status changes (no scheduled resurface — documented simplification). All mutations broadcast `conversation_updated` on `inbox:{workspaceId}` so every open inbox reacts live without polling. Rate limiting added (fixed-window, Postgres-backed): widget create/contact/message routes (10/10/30 req per min per IP) and auth signup/signin (5/300s and 20/60s). `rate_limit_windows` table + `increment_rate_limit` SECURITY DEFINER function in migration 005; fails open so a broken table never blocks traffic. Caveat found in phase 5: migration 005 had never actually been applied to the hosted project, and because the limiter fails open, every limit was silently a no-op with nothing in the logs to say so. Applied now. The lesson is that fail-open needs a startup assertion or a log line, otherwise "no errors" and "not running" look identical — worth doing before submission.
5. **Done.** Knowledge base. TipTap editor (StarterKit, which bundles Link and Underline in v3) at `/knowledge-base/[articleId]`; a new article is created as a draft server-side and the editor redirects into it, so there is no id-less form state. Bodies are sanitised on write against a nine-tag allowlist (`lib/kb-html.ts`), not on read, so the database only ever holds safe markup and every consumer inherits it. Category CRUD; deleting a category reassigns its articles to uncategorised (`on delete set null (category_id)`) and never deletes content. Public help centre at `/kb/[workspaceSlug]` and `/kb/[workspaceSlug]/[articleSlug]`, outside the `(dashboard)` group, no auth, no session. Search is Postgres full-text through `public.search_kb_articles`, a SECURITY INVOKER RPC so the caller's own policy applies — needed because PostgREST cannot order by `ts_rank`. Query strings are reduced to alphanumeric tokens with a prefix match per token, which is both injection-safe for `to_tsquery` and what makes suggestions useful mid-word. Widget auto-suggest via `/api/widget/kb-search` (same Origin allowlist as phase 2, 60 req/min/IP/workspace), debounced 300 ms, minimum 3 characters, up to 3 results, each keystroke aborting the previous request so out-of-order responses cannot win. Clicking a suggestion opens the public article in a new tab rather than an in-widget reader — documented trade-off, see the comment on `renderSuggestions`. Coverage: `supabase/tests/rls_isolation.sql` (92 checks, now including an `anon` probe), `npm run test:kb-html`, `npm run test:kb-smoke`.
6. **Done.** AI issue summarization + auto-reply drafts. Both use `gpt-5.4-mini` through the Responses API with `reasoning.effort: none` and an 8s timeout (`maxRetries: 0` so that is a hard ceiling). Opening a conversation fetches and renders the thread immediately; the summary loads in its own panel and never blocks the view. First summary: last ~40 messages or a 10k-char budget, whichever is smaller, from the recent end. Later: existing summary + messages since `ai_summary_message_count`. Failures show "Summary unavailable" with a manual retry — no automatic loop. Rate-limited per workspace (20 summaries / 15 drafts per minute) via `rate_limit_windows`, because each call has a dollar cost. Drafts are button-triggered in the composer, never auto-sent; context is the current summary plus verbatim messages after it (or a capped recent window if no summary yet), plus the top 2–3 `search_kb_articles` hits for the customer's latest message. The draft lands in the composer as editable text the agent can revise, discard, or send.
7. **Custom domains done; analytics not started.** Migration 20260830150000 adds `custom_domain_status` (enum none | pending | verified | error) and `custom_domain_verified_at`, plus a hostname-format check mirroring the router's expectations and a consistency check tying status to the presence of a domain. Applying it surfaced a workspace sitting at `custom_domain = ''`, cleared by the migration — an empty host would have collided on the unique index the moment a second workspace did the same. Settings → Custom domain (admin-only) connects a domain via `POST /v10/projects/{id}/domains`, stores it as `pending`, and renders the DNS records from `GET /v6/domains/{domain}/config` for this project rather than Vercel's published defaults. "Check verification" is on demand and promotes to `verified` only when Vercel reports ownership verified **and** configuration not misconfigured, because ownership alone means no certificate; `custom_domain_verified_at` is written once and never cleared. No polling job. SSL needs no application code — Vercel provisions and renews it once the domain verifies, and the middleware passes `/.well-known/*` through so renewals cannot be broken. Routing: `middleware.ts` resolves the Host header first; app hosts fall through, an unclaimed host falls through, a **claimed-but-unverified** host gets a bare `no-store` 404 on every path (the hijack guard — `custom_domain` is only what an admin typed, so an unverified claim must resolve to nobody's KB), and a verified host serves `/` → `/kb/{slug}` and `/{article}` → `/kb/{slug}/{article}` and nothing else. Dashboard, auth, API, and deeper paths 404 on a custom domain, so a customer-controlled hostname never gets a same-origin foothold. The decision is a pure function in `lib/custom-domain.ts` over `(pathname, route)`; `npm run test:custom-domain` asserts every row of that table including the guard. Lookup uses the service role, not `anon`, because `custom_domain`/`custom_domain_status` are deliberately outside `anon`'s column grants; it builds its own client rather than importing `lib/supabase/admin.ts`, which imports `server-only` and would throw in the Edge middleware bundle. 30s in-process cache, so a just-disconnected domain can serve for up to 30s from a warm isolate; disconnect clears our row before detaching at Vercel. Deferred within this scope: background verification polling, changing a domain without disconnecting first, apex+www pairs.
8. **Done.** Analytics dashboard at `/analytics` (dashboard-only, auth-gated). Four metrics, all computed on-the-fly via aggregate SQL RPCs (SECURITY INVOKER, no materialized view): (1) First-response time — avg / median / P95 in seconds, computed as first agent message minus first contact message per conversation, no snooze adjustment, disclosed in the UI tooltip; (2) Resolution rate — resolved / total conversations, all-time, no date range picker (explicitly deferred); (3) Busiest hours — message volume by hour-of-day (UTC 0–23), CSS-only horizontal bar chart, no charting library; (4) Per-agent breakdown — resolved conversations and avg first-response time per team member. All four queries run in parallel (Promise.all). Empty-data state handled explicitly at each section — fresh workspaces never see a broken chart or a divide-by-zero result. Verified against the hosted project: as a real member the functions return the workspace's rows; as an `authenticated` user with no profile all four return zero rows, which is the tenant-isolation proof for the no-parameter design (there is no `workspace_id` argument, so RLS is the only gate). `anon` is explicitly revoked — Supabase's default grants EXECUTE on every public function to `anon`, which would otherwise publish all four at `/rest/v1/rpc/`; same revoke pattern as the bootstrap functions in migration 000200.

Two things this phase surfaced, both worth keeping:
- **The migration was written but never applied**, and the only symptom was a PostgREST error at the UI ("Could not find the function … in the schema cache"). This is the *second* occurrence of the exact failure recorded in phase 4 for migration 005. Local `supabase/migrations/*.sql` is not evidence that the hosted schema has it — remote migration versions in this project do not even match the local filenames. Check `list_migrations` against the directory before assuming a function exists.
- **Postgres `numeric` arrives over the wire as a JSON string**, while `bigint` arrives as a number. So `avg_seconds` is `"53"`, not `53`. The generated-type convention of calling `numeric` a `number` is a latent bug — `row.avg_seconds + 1` would produce `"531"`. Types now declare these as `string | null` and every aggregate value goes through one `toNumberOrNull` helper that also turns an unparseable value into null instead of letting `NaN` render.

Known real-scale limitation: at tens of thousands of conversations the first-response CTEs will need a pre-aggregate layer or indexes on (conversation_id, sender_type, created_at); documented in the UI, not silently skipped.

**8b. Done.** SLA tracking with business-hours awareness. Five migrations, `20260831110000`–`20260831110400`, all applied and verified against `list_migrations`.

The load-bearing piece is `private.business_seconds_between(start, end, hours_start, hours_end, days[], tz)`. It walks calendar days in the workspace's own timezone and, per working day, materialises that day's window as two `timestamptz` values and adds the overlap with the span. Every case falls out of the overlap arithmetic with no special branch: starting or ending outside hours, spanning a weekend, spanning months, or lying entirely outside hours. Anchoring each window to local wall-clock and converting back to absolute time *per day* — rather than doing the arithmetic in naive local time — is what makes it DST-correct; a transition day yields a window of its real length and no later day is shifted. It lives in `private` so Supabase's blanket EXECUTE-to-anon does not publish it over REST. Cost is O(calendar days), which is why the target columns have upper bounds and the breach summary only scans unresolved conversations.

Tested directly before anything was wired to it: `supabase/tests/business_hours.sql`, 30 cases with hand-computed expectations against a stated reference calendar (which the file itself asserts, so a wrong weekday cannot make a wrong answer look right). All 30 pass on the hosted project, including a span crossing the 2026-11-01 US DST transition and a case that pins the fixture's own wall-clock length at 25 hours. The snooze trigger and the RLS isolation of the two read functions were probed separately on the hosted database inside aborted transactions.

**A real bug this found.** The first `business_days` check used `array_length(business_days, 1) between 1 and 7`. `array_length` returns NULL (not 0) for an empty array, NULL BETWEEN is NULL, and a CHECK treats NULL as satisfied — so `business_days = '{}'` was accepted, which makes every span measure 0 business seconds and silently pins every conversation in the workspace to "on track" forever. Migration `110400` replaces it with `cardinality()`. The lesson is the same one phases 4 and 8 recorded in a different key: reading the expression is not testing it. `business_hours.sql` now probes the constraint *as deployed* (via `pg_get_constraintdef` re-applied to a temp table) so it cannot pass because the expression was retyped correctly in the test.

SLA status is computed on read and never stored — `public.get_conversations_sla(ids[], unresolved_only)`, SECURITY INVOKER, no `workspace_id` argument, so RLS is the only gate exactly as in phase 8. A stored breach flag is wrong the moment time passes with no write: a conversation 29 minutes into a 30-minute target becomes a breach with no row change to trigger on. First response is first contact message → first agent reply after it, or → `now()` while unanswered, with no snooze adjustment (snoozing an unanswered customer should not buy more time to answer them). Resolution is first contact message → `resolved_at` or `now()`, minus banked snooze and minus any snooze in progress, floored at 0. Because a resolved row's endpoint and snooze total are both frozen, its elapsed value can never change again — it cannot drift into breach after the fact. Three states from `private.sla_state`: breached above target, approaching in the final 20% inclusive, on-track below. A conversation with no contact message has no clock and no badge, which is the normal state of an agent-initiated thread.

UI: a coloured dot in each inbox list row and a labelled pill in the thread header (`components/sla-badge.tsx`), both fed by one RPC for the whole page rather than one per row. The inbox client re-fetches on a 60s timer as well as on list changes, because the state moves with `now()` and there is no write to broadcast. Detail is in a `title` attribute rather than a hover card so it costs nothing across 50 rows and works on a row that is itself a click target. Analytics gets an "SLA breaches" card counting unresolved conversations past either target, workspace-wide, with the first-response and resolution components broken out (they overlap, so the headline is counted separately rather than summed) — unresolved only, because a conversation closed late is history, not a worklist item. Settings gets an admin-only panel for both targets, hours, working days and timezone; agents see the same values read-only, since the numbers explain the badges in their inbox. The write goes through the caller's own client so `workspaces_update_admin` is the real gate, verified on the hosted project (admin update 1 row, agent update 0 rows).

Known limitations, none silent: no public holiday calendar, so a national holiday counts as a working day; overnight business hours unsupported by constraint; the timezone picker is a curated list of 11 zones rather than the full IANA set, and a workspace already on a zone outside the list keeps it; `formatDuration` moved from `lib/analytics.ts` to `lib/sla.ts` (and is re-exported) because the badge needs it in a client component and the analytics module is `server-only`.

`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_APP_URL`, `POSTMARK_SERVER_TOKEN`, `POSTMARK_FROM_EMAIL`, `POSTMARK_INBOUND_ADDRESS`, `POSTMARK_INBOUND_WEBHOOK_USER`, `POSTMARK_INBOUND_WEBHOOK_PASS`, `OPENAI_API_KEY`, `VERCEL_API_TOKEN`, `VERCEL_PROJECT_ID`, and `VERCEL_TEAM_ID` only if the Vercel project sits under a team rather than a personal account (the Domains API requires it in that case and rejects it otherwise, so it has no safe default).

## Evaluation criteria to keep in view
System design, production readiness (error handling, logging, validation, rate limiting), AI integration (prompt design, cost awareness, fallback handling), real-time architecture (reconnection, message ordering), email engineering (threading, deliverability), frontend quality, security (auth, XSS/CSRF, tenant isolation), and trade-off decisions (documented, not just made).
